# Testcase-AI-first
# Support Draft Service

Сервіс обробляє звернення в підтримку: приймає їх вебхуком, шукає статті в базі знань,
генерує чернетку відповіді через LLM, дає оператору підтвердити або відхилити її та
надсилає підтверджену відповідь клієнту через API хелпдеску.

Деталі архітектури: [docs/architecture.md](docs/architecture.md). Постановка: [docs/task.pdf](docs/task.pdf).

## Запуск

Потрібні Docker і Docker Compose.

```bash
git clone https://github.com/andriynavr07/Testcase-AI-first.git
cd Testcase-AI-first
docker compose up --build
```

Це піднімає 4 сервіси: `db` (PostgreSQL), `api` (вебхук, UI, міграції, сід бази знань),
`worker` (генерація чернеток і відправка відповідей), `mock-helpdesk` (мок хелпдеску).
`worker` стартує після того, як `api` стане healthy (тобто після міграцій).

| Що | Адреса |
|---|---|
| Інтерфейс оператора | http://localhost:8000/ |
| Вебхук | `POST http://localhost:8000/webhooks/helpdesk` |
| Health | http://localhost:8000/health (200, `OK`) |
| Мок хелпдеску, що «отримав» клієнт | http://localhost:9000/replies |

### Режими LLM
- **Без ключа (за замовчуванням).** Нічого налаштовувати не треба. Сервіс робить реальний запит до
  Anthropic API з навмисно невалідним ключем (відповідь 401 відкидається) і використовує статичну
  чернетку із загальною затримкою 5-30 с. Такі чернетки позначені `[mock-чернетка]` в UI.
- **З ключем.** Створіть файл `.env` поруч із `docker-compose.yml`:
  ```
  ANTHROPIC_API_KEY=sk-ant-...
  ```
  і виконайте `docker compose up --build -d`. Модель за замовчуванням `claude-haiku-5-5`
  (змінюється через `LLM_MODEL` в `app/config.py`).

### Інші змінні (`.env`, необов'язково)
- `WORKER_CONCURRENCY` (25): кількість паралельних викликів LLM
- `CHAOS` (1): `0` вимикає випадкові збої мока хелпдеску (для детермінованих перевірок)

## Як перевірити

Нижче `curl` для bash; у Windows PowerShell використовуйте `curl.exe` і JSON із файлу
(`--data-binary "@evt.json"`).

1. **Health:** `curl -i localhost:8000/health` дає `200 OK`.
2. **Вебхук:**
   ```bash
   curl -i -X POST localhost:8000/webhooks/helpdesk -H 'Content-Type: application/json' -d '{
     "event_id":"evt_1","ticket_id":"T-1","customer_email":"user@example.com",
     "message":"Не можу експортувати звіт у PDF",
     "reply_url":"http://mock-helpdesk:9000/tickets/T-1/replies"}'
   ```
   Перший запит дає `202`, повтор тієї самої події `200 {"status":"duplicate"}`.
   Через 5-30 с чернетка з'явиться в UI, де її можна відредагувати й підтвердити або відхилити.
3. **Симуляція навантаження і дублів:**
   ```bash
   python scripts/simulate.py --n 500 --dup-ratio 0.1
   # без Python на хості:
   docker compose run --rm api python scripts/simulate.py --n 500 --dup-ratio 0.1 --base http://api:8000
   ```
   Скрипт шле звернення, частину з них по 3 рази одночасно, і друкує розподіл статусів і затримку
   вебхука. Очікується: `202` рівно `n` разів, решта `200`, затримка значно менша за 2 с.
4. **Масове підтвердження для тестів** (замість кліків у UI):
   ```bash
   docker compose exec -T db psql -U app < scripts/approve_sim.sql
   ```
5. **Відсутність дублів відповідей:** `curl localhost:9000/replies` показує по кожному звернення
   `replies_stored` (скільки відповідей «отримав» клієнт) і `delivery_attempts`.
   Навіть при випадкових 5xx і таймаутах `tickets_with_duplicates` має бути `0`.
6. **Ліміт LLM:** `select count(*) from rate_limit where count > 60;` дає `0`.

## Архітектура коротко

- **Вебхук швидкий.** Лише транзакційний запис події й звернення в Postgres. LLM не викликається,
  тож відповідь за мілісекунди (вимога: менше 2 с).
- **Дублі й повтори подій.** `event_id` це PRIMARY KEY, вставка через `ON CONFLICT DO NOTHING ... RETURNING`.
  Одночасні дублі безпечні, бо рішення приймає БД, а не перевірка в коді.
- **Звернення не втрачаються.** Черга в Postgres (`FOR UPDATE SKIP LOCKED`) із lease. Пік 500 за
  10 хвилин лише збільшує чергу. Якщо воркер упав, звернення підхоплюється після спливу lease.
- **LLM.** Затримка 5-30 с компенсується пулом потоків (25), а ліміт 60 запитів/хв на весь сервіс
  тримається лічильником у БД (`rate_limit`), тому коректний і для кількох воркерів.
  Запити режиму без ключа теж рахуються в ліміт. Збій виклику: повернення в чергу, `failed` після 5 спроб.
- **База знань.** 8 коротких AI-згенерованих статей про вигаданий продукт «Планфлоу»
  (`data/articles.json`), зберігаються в Postgres, пошук full-text із префіксним збігом.
- **Відправка клієнту.** Одна відповідь на звернення (UNIQUE), успіх лише `201`, повтори з експоненційною
  паузою на 5xx і таймаути (максимум 8 спроб), 4xx одразу `failed`, заголовок `Idempotency-Key`.
- **Мок хелпдеску.** Випадково повертає 5xx, зависає, а також «обробляє запит, але відповідає із запізненням»
  (найскладніший випадок для дубля). Дедуплікує за `Idempotency-Key`.

## Прийняті рішення та відомі обмеження

- **Дубль відповіді при збої.** Якщо хелпдеск обробив запит, а відповідь до нас не дійшла, ми
  повторюємо з тим самим `Idempotency-Key`. Гарантія «без дубля» повна лише якщо хелпдеск підтримує
  цей ключ (мок підтримує). Для хелпдеску без підтримки ключів повного захисту дати неможливо.
- **Немає авторизації в UI оператора.** Завданням не вимагається, у проді потрібен вхід.
- **Пошук лексичний.** Без синонімів і справжньої лематизації (українська морфологія наближена
  префіксами слів). Наступний крок: `pg_trgm` або ембединги.
- **Повторне звернення з тим самим `ticket_id`.** `ticket_id` унікальний, тож нове повідомлення в уже
  існуючому тікеті (інший `event_id`) записується як подія, але нового звернення не створює.
  Для підтримки діалогів треба окрема таблиця повідомлень.
- **Опитування БД.** Воркери перевіряють чергу раз на секунду. Для заданого навантаження достатньо,
  для більшого варто `LISTEN/NOTIFY`.
- **Історія комітів «як є».** Два ранні виправлення (`PYTHONPATH` для Alembic і код `200` для дубліката)
  потрапили в один коміт, а `CLAUDE.md` і документація додані в кінці. Історію не переписано.
